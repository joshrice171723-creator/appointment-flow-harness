# V2.6.1.2 refactor harness

Use this mode with the shared Rails architecture, coding, performance, and review standards. Start from the existing implementation and the user's requested scope. The normal caller and its observable behavior are the reference.

## Make the change easy to review

- Trace the entry point, contract, and rule owners before editing. Preserve inputs, results, error behavior, scope, ordering, limits, and side effects that callers rely on.
- Name meaningful steps so someone can find the rule they would change. Keep caller-specific work near that caller. Give shared operations and independently testable business transactions a clear owner.
- Separate a change in structure from a change in how work is done. Measure a behavior-preserving structural change on its own. Evaluate query changes as separate candidates so their cost and effect are visible.

## Compare equal results and real work

- Use plain Active Record for application queries. Evaluate its actual behavior before adopting a replacement. A different API, fewer source lines, or fewer round trips alone provides no evidence of improvement.
- Measure the same complete operation before and after. Assert the same result. Include a normal case and increased data that the operation could touch even though the caller's result stays the same. Where relevant, also exercise more eligible work, failure, and retry.
- Compare statements, rows returned, models instantiated, rows written, and lock scope where applicable. When an option trades more round trips for less transferred data, measure the full operation before deciding. Report elapsed time with the conditions that affect it.
- Keep filtering before materialization. Watch for a change that moves the work from the database into Ruby, loads previously excluded data, repeats an aggregate or query, or makes an existing bound ineffective.

## Grade what the evidence supports

- Choose the smallest understandable change that preserves the contract and has an acceptable cost on the measured workloads. If an alternative worsens a material metric, record the actual difference and the reason any remaining cost is justified.
- Apply the existing evidence-based rubric to the changed scope. A verified breach of the plain Active Record rule still requires revision. If closing it needs a change outside the requested scope, show the best verified in-scope result, retain the REVISE grade, and name the specific dependency. Keep results from discarded alternatives for comparison.
- Use the same focused checks after repairs and report the exact source and workload graded. The AI owns the checks and the grade.
