# Appointment Flow source comparison

Ten archived app snapshots were reviewed in random order by a fresh Codex session. The review used the actual Rails routes, controller excerpts, and selected refresh, reply, reminder, and follow-up code. Rankings apply to those paths. Query costs are source inferences unless a historical measurement is identified explicitly.

## Findings

- **Controllers:** V2.4.1.1.0 and V2.3 lead. The app named V3 still sends most API routes to custom actions on a workspace controller. For example, a recorded reply can be a resource handled by `RepliesController#create`.
- **Workflow readability and changeability:** V2.4.1.1.0 led the supplied follow-up path. One service owns the lock, replay check, revision check, and both writes. V2.3 and V2.4 were close on the sampled service paths.
- **Performance:** V2.4.1.1.0 bounds the reminder visit loop and uses per-visit existence checks. Its refresh still reads the source feed and indexes cached visits by practice. V2.3 had the strongest local refresh pattern shown, with referenced-patient loading and changed-only saves. No comparable runtime results exist across all ten builds.
- **Error handling:** V2.4.1.1.0 still rescues `StandardError` at the refresh boundary and marks practices unhealthy. V2.3's refresh can classify a local SQL failure as source unavailability. Both paths warrant checking through their actual callers.

V2.4.1.1.0's existing run recorded 2 SQL statements and 12 materialized records for the visit list, and 28 statements and 17 materialized records for a six-send batch, both before and after adding 500 unrelated historical visits. These are historical results for those two operations. The refresh path was outside that measurement. The technical freeze names application commit `e4ffeb9800e1a7cce23cdeb7d31843177fc1aa90`. The archived HEAD is `213c425b32ac`, which also contains handoff and dependency metadata changes.

### Comparative judgment

- **Rails controller conventions.** D and H lead. Their routes express scope and mutation through standard actions, including D’s global refresh and H’s contact update. B is close on action names, with a clinic URL for a global refresh. I follows with one custom assignment action. J uses standard actions across much of the API, with several older-style member commands still present.
- **Readability and changeability.** D leads for the supplied follow-up path because the service keeps revision checking, replay, locking, and both writes together. H and I are close. H makes refresh and reply stages easy to locate, and that ordering explains why STOP depends on refresh. I makes the follow-up rules particularly easy to trace, while its controllers own refresh sequencing for replies and reminders. A documents its transaction split clearly. G puts more receipt validation in the rule owner, with the public handoff omitted.
- **Likely database work.** For reminder selection, B, D, and I lead on the visible date predicates. D still builds ownership over all upcoming visits, and I refreshes the clinic and materializes its contacts before processing the bounded set. H leads among the visible clinic refresh implementations for restricting source patients to referenced IDs and saving changed imports, though frequent refreshes can dominate that advantage. G shows the strongest appointment-source predicate, conditional on the omitted refresh caller supplying it. C, E, F, and J show broader application-side scanning on their traced paths.

D makes follow-up changes easiest to localize, H limits the scope of a refresh, and B gives the reminder batch a bounded visit relation without an inline refresh. Those advantages apply to different operations. The supplied code gives no basis for a single performance winner across refresh, reply, and reminder workloads.
