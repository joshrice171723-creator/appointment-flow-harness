# V2.7.1.1.1 refactor mode

Apply this mode with the V2.7.1.1.0 architecture, coding, performance, and review standards when the user asks to improve existing code. Start from the existing implementation. Preserve its public behavior, required data boundaries, and documented business rules.

1. Trace the requested entry point. Record its inputs, observable results, and rule owners. Identify the files and callers the requested change actually touches.
2. Capture a focused baseline through the real caller before editing. Check the behavior and the database work that the proposed change could affect. Keep the task scoped to this behavior and its necessary verification.
3. Make the public entry point read in execution order. Keep screen-specific work in named private controller methods. Introduce a service when actual callers share the operation or when it has its own business rules and transaction boundary that warrant independent testing. Use standard Active Record for application queries.
4. Run the same focused checks after the change. Compare equal results, query counts, returned rows, and growth where relevant. Use the V2.7 grading rules on the changed scope. A defect outside that scope can be reported separately. Require focused evidence from the real caller for the claims in the final grade.
5. Save the diff and evidence. Record any verified regression or unmet standard. Repair within scope and regrade. When the standard and the existing contract cannot both be met within the requested scope, show the evidence and report what would need to change.
