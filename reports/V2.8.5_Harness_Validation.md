## Acceptance checks

### Original-app refactor

1. Run the same five HTTP requests on each frozen version.
2. Compare response bodies and cursors on both test data sets.
3. Check access for a clinic member and an authorized guarantor.
4. Check that the app denies access when the authorization no longer applies.
5. Check missing and reassigned appointments in the focused Rails tests.
6. Compare statement counts, returned rows, Active Record objects, elapsed time, and buffer use.
7. Identify the query plan step that grows when the response stays the same.
8. Compare the external PMS schema before and after the refactor.
9. Verify that the app's PMS connection can read and cannot write.
10. Run the Active Record check. Record existing findings outside the refactor scope.

The larger test data set adds 5,000 older mirror appointments and 15,000 tracked visits. Both data sets use the same patient pages. The five requests cover two past pages, upcoming history, patient details, and a patient with tracked visits only. The test measures each request five times. It records query plans in a separate run. The initial refactor session received no independent test cases.

### Standalone rebuild

1. Save the first build and the reviewed build as separate Git revisions.
2. Run the Active Record check on the migrated database.
3. Compare all 44 independent results with the V2.7 results.
4. Record sends, contact holds, staff reviews, and confirmations in the shared-recipient cases.
5. Compare the small, large, and repeat workloads.
6. Verify that the app uses only the source fields in the supplied schema.
7. Test a small rule change in a separate copy.

The first build `0b2191e` and the final build `84c2964` each passed 42 of 44 independent checks. Both returned the correct appointment IDs and day totals. Two checks found the week count missing. All historical shared-recipient cases passed.

Both builds sent 24 reminders in 19 statements. The original used 119 statements for the same send workload. In a separate two-send case, 2,000 extra patients increased the rows returned to Rails from 10 to 2,010. Both data sets used 19 statements. The largest query returned 2,002 rows on the larger data set.

The final build passed its own rubric. It passed the Active Record check, 32 Rails tests, and the browser checks. The independent comparison found the missing week count and measured the cost of reading raw contact data. V2.7.3.1.0 remains the working rebuild baseline.

The next reminder test must measure source rows, source bytes, and writes to the app mirror. Keep the visible outcomes the same when extra source rows do not change eligibility. Add a control where a source contact change must change the result. A source lookup must preserve correct recipient selection before its performance can pass.

### Original reminder job and PMS

The reminder job test used the original revision `db037d7`. It kept the same 24 appointments and added 2,000 patients with no appointments. Both first ticks opened 16 tickets and recorded 16 fake sends. Each retry added zero tickets and sends. The first ticks used 239 statements. The retries used 88.

The PMS response grew from 8,893 to 393,743 bytes per tick. The first refresh affected 2,000 more app rows. The larger retry fetched the same data and affected only the sync row. [Job benchmark CSV](../benchmarks/Original_Reminder_Job_PMS_Workload.csv)
