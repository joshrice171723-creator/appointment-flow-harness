## Matched reminder workload after the repairs

The rerun used the same synthetic scenario for both implementations. It exercised the complete reminder tick with 60 clinics and 4,000 due appointments. Both apps sent to the expected appointment IDs. Two identical repeats produced zero extra sends. Delivery was simulated. Fixture setup is outside the tick counts.

| Measure | Original `db037d7` | Repaired rebuild `5f2500c` |
| --- | ---: | ---: |
| Distinct simulated sends, first tick | 4,000 | 4,000 |
| Write statements, first tick | 12,127 | 420 |
| Extra sends over two identical repeats | 0 | 0 |
| Write statements per repeat | 7 | 0 |
| Affected rows per repeat | 1 | 0 |

The rebuild used about 96.5% fewer first-tick write statements in this workload. The original stores additional per-send history records. The rebuild still reads a clinic’s full appointment history during refresh. The original bounds its appointment read, though it reads all source patients. The original also uses a direct PostgreSQL source connection outside Rails instrumentation. Interpret Rails read counters with that instrumentation boundary in mind.

The paired rerun overlapped other local verification. Its elapsed times are omitted from the headline comparison. The earlier Workbench build timing and the paired timing came from separate runs. Neither establishes production latency or a general speed ranking.

## Limits of the older score

The V1.1.0 aggregate combines workflow coverage and weighted database work. It awards zero where a build does not support a tested response contract. That is useful for showing differences in scope, including the legacy rebuild’s patient-history and guardian contract gaps. Use matching cases and their raw counters for efficiency claims. The older 16-case, 44-case, and 60-case results use different workloads and cannot establish one overall ranking. The historical CSV retains the original evaluator outputs for traceability.

## Open work

The source audit found a duplicate PMS refresh on a due tick. The maintenance path refreshes the clinic, then the send path refreshes it again. A scoped refactor can remove the second read if it keeps clinic locking, freshness, and retry behavior intact. The source audit also identified full clinic-history reads on the refresh path. It did not measure the effect of a proposed fix.

The Workbench browser checks cover their configured flows. The frontend parity audit uses the ten pinned screenshots and the written requirements, plus the original app for interaction states that the screenshots omit. Parity remains an open evaluation. The matched reminder run verifies sends and repeat behavior.
