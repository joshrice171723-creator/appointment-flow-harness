# V2.6.1.1.0 clean-room experiment

V2.6.1.1.0 combines the workflow planning and grouped-write guidance from V2.5.1.0.0 with the AI repair loop and fresh-database verification from V2.5.1.1.0. It moves database evidence into implementation and requires the AI to try a small rule change in a disposable copy. The comparison suite lives outside the builder's project. [Harness design](V2.6_Harness_Design.md) · [Shared launch prompt](V2.5_Launch_Prompt.md)

## What the builder changed after measuring

The reminder command initially loaded the source appointments and their local copies on every run. The builder measured a retry with 1,200 additional later appointments. It still had zero extra reminders to send, yet Rails received 2,410 rows and instantiated 2,406 objects. The builder moved the comparison into PostgreSQL so only new, changed, or missing records came back. The identical retry then returned 8 rows across the whole command and instantiated 4 objects, with zero extra sends or database writes. The calendar continued to show the expected appointment rows. This repair preceded the first independent grading checkpoint.

A separate test with 600 later appointments reproduced the result on the frozen implementation. After the first import, the same-clock retry returned 10 rows across the workflow, instantiated 5 models and performed zero writes. `EXPLAIN ANALYZE` verified that PostgreSQL still compared 602 source and local appointments and returned zero rows from that comparison. This removes transfer and Ruby object loading on an unchanged retry. The initial calendar import still does work proportional to newly discovered appointments. [Rails event payloads](https://guides.rubyonrails.org/v8.1/active_support_instrumentation.html#sql-active-record)

## Active Record and handwritten SQL

The V2.6.1.1.0 reminder, reply and calendar use Active Record for clinic/date filters, bounded loads, `pluck`, preloads, aggregates and writes. The source refresh comparison uses `find_by_sql` with Rails-built scopes, a PostgreSQL full outer join and a null-safe row comparison. That one query checks for missing source rows and changes from the same database snapshot. Contact normalization and calendar dates use smaller SQL expressions inside Rails scopes. The original's direct replica calls use handwritten SQL through its raw `PG` connection and are counted separately. The SQL trace includes the application call site so a reader can verify which Ruby constructed the statement. ## What independent grading added

The first application checkpoint passed all seven configured checks. Independent review still returned **REVISE**. It reproduced replies applying STOP to a corrected address instead of the displayed delivery, contact verification values in Rails request logs, old work items left open after late PMS updates, and a fresh test setup loading demo seeds. It also measured the leadership request growing from 9 to 183 SELECTs when the fixture grew from 2 to 60 clinics.

The builder repaired those paths. The new opt-out uses the displayed delivery's address, request logs mask submitted contact data, old open work is in scope for reconciliation, and fresh test setup uses the test fixtures. Clinic-local reporting totals are grouped in the database. The leadership request now takes six SELECTs at both 2 and 60 clinics and preserves the tested month-boundary result. The independent regrade passed 27 Rails tests and 205 assertions on a fresh database. Two browser smoke tests and all seven configured checks passed.

The reviewer also ran a real changeability exercise in a disposable copy. Moving the follow-up from three clinic-local days to two changed one production file, `ReminderRun`. The focused integration test passed 17 assertions covering the new day, the absence of a follow-up at three days, and the existing seven-day initial reminder. The shipped timing follows the assignment's three-day policy.

## What the shared benchmark added

The first rubric pass still had one insert per fake reminder. The separate 24-reminder comparison found 41 statements, including 26 writes. A disposable trial grouped the attempts in the existing transaction, passed the same 16 workload checks and stored the same 24 sends with 18 statements and 3 writes. I sent those measurements back to the builder as a follow-up on its own code.

The builder reproduced the improvement through the real staff HTTP route. That path went from 43 statements to 20, with 26 writes reduced to 3 and the same 49 affected rows. The extra statements come from HTTP request handling. Both runs stored equivalent audit fields and the same attempts. The unchanged retry wrote zero rows. Focused tests covered the failed-SMS email fallback, two independent connections attempting the same clinic run, and an injected failure after a database write. The final independent regrade passed 12 focused tests with 95 assertions. The final local gate passed all seven checks with 29 Rails tests, 233 assertions and two React tests. Both browser tests passed again.

The combined process exposed different issues at different points. The builder's first growth check found the costly unchanged refresh, the independent grader found the reporting and safety issues, and the shared benchmark exposed work that passed the first grade. Keep these three checks in future comparisons. Require a separate result for first-time import, unchanged retry, and a larger eligible batch. When writes rise per eligible row, have the AI test a grouped write or establish the per-record behavior that requires separate writes.

## Blind comparison of the frozen builds

Two independent AI reviewers read the same anonymized source excerpts and benchmark results in opposite orders. Both would continue from V2.5.1.1.0 and tied it with V2.6.1.1.0 for overall measured database work. V2.5.1.1.0 kept the first-run work flat with 600 later source appointments. V2.6.1.1.0 had the fewest statements for 24 reminders and their retry, and the same number of rows returned for the scoped reply.

The readability ratings varied by review order. One reviewer put V2.5.1.1.0 first and tied V2.6.1.1.0 with V2.5.0.0.0 for second. The other put V2.5.0.0.0 first and V2.6.1.1.0 second, citing the older build's named reply rejection reasons. The original `appointment-flow` had the most handoffs to trace but scored first or tied first on locating the reminder rule. Those reviews inspected source. The disposable cadence-change test above is the executed changeability check.

The experiment supports keeping the V2.6 evidence workflow. The cold calendar projection remains its largest measured cost, and the blinded comparison still favors V2.5.1.1.0 as an application starting point. These results cover one rebuild and its measured follow-up with standalone Codex.
