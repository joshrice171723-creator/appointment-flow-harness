## General lesson for the next harness candidate

Group related code by responsibility and data ownership. Use descriptive namespaces and matching folders for meaningful system boundaries. Follow the framework's naming and loading conventions.

Separate database connections and external APIs can indicate these boundaries. Infer the grouping and its domain name from the project. Use the organization to help a reader identify ownership and find the rule that needs to change.

The reviewer should trace where data comes from, who controls it, which code reads or changes it, and where a related business rule belongs. Let the implementation's actual responsibilities determine its grouping.

The missing PMS folder is Joshua's observation about this application. Keep the example in the experiment record. The harness should express the general ownership rule and let builders infer a suitable structure for each project.
