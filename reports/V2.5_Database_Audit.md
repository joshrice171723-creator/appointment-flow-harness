## Original baseline

The pinned original source is `appointment-flow` on `main` at `db037d7932b13fc4d735106e0fa199815fb2d22c`. Its Front Desk appointment list uses Active Record through `DeskController#appointments` and `AppointmentsQuery`. Its scheduled reminder worker goes through `ReminderRunner.tick` and can refresh PMS and process multiple enabled clinics. `PmsReplica` sends handwritten SQL through a dedicated `PG.connect` session. Workflow locks also use handwritten PostgreSQL advisory-lock statements. The audit ZIP includes its original source call inventory. [Original source and revision](https://github.com/joshrice171723-creator/appointment-flow/tree/db037d7932b13fc4d735106e0fa199815fb2d22c)

It went from 13 to 11 application SQL statements and 2,485 to 132 instantiated Rails objects. That documented result demonstrates less work inside a report request. The matched reminder and appointment-list measurements are shown below. ## What the benchmark measures

Each build started from its pinned Git revision in a disposable copy. Ruby was 3.4.10 and PostgreSQL was 17.11. The original used its locked Rails 8.1.3.1. The standalone builds used Rails 8.1.4.1. Rails test ran with seed 41531 and one worker. The benchmark used one private loopback PostgreSQL instance with a separate database per build. The four benchmark runs were serial. Full command lines, start times, elapsed times, exit codes, database configuration overrides, PostgreSQL logs, and Rails SQL events are in the evidence ZIP.

The clock stayed at noon in Chicago on November 16, 2026. Each eligible appointment was scheduled seven days ahead at 2 p.m. local time. Patients had fictional, unique email addresses. The scenarios used two eligible appointments, two plus 600 completed source appointments from 2024, and 24 eligible appointments.

- **Reminder batch** means one run for one clinic. It covers the application's source reads, eligibility and duplicate checks, simulated sends, and database writes. The 24-appointment case repeated the same batch at the same clock to check for repeat sends.
- **Front Desk appointment list** means one authenticated HTTP GET for November 23, the date of the eligible appointments. This is the backend endpoint the Front Desk calendar uses. The measurement covers the list and status data returned by Rails. Browser rendering and the sign-in request are outside that operation. The request goes to `/api/appointments` in V2.5.1.0.0 and `/api/clinics/:id/appointments` in the other two standalone builds.

Counts below include query statements, transaction boundaries, and explicit database settings such as `SET LOCAL`. Rails schema and session metadata, cache hits, and fixture operations have their own counters. `Write statements` includes attempted writes that affected zero rows. Active Record objects counts Rails instantiation events, including repeated loads of the same record. SQL result rows and affected rows are available in the CSV. Those rows describe data returned or changed, with query plans needed to determine how much PostgreSQL scanned.

- **V2.5.0.0.0.** `PmsSync#read_snapshot` uses the Active Record replica connection for clinics, appointments, and patients. `AppointmentsController#index` groups on `left(wall_start, 10)` through `Arel.sql`. Its review lookup embeds `jsonb_object_keys` in a relation predicate. The work-items search uses an `ILIKE` fragment. Source locations are `backend/app/services/pms_sync.rb:31–45`, `backend/app/controllers/api/appointments_controller.rb:11`, `backend/app/controllers/concerns/visit_views.rb:18–20`, and `backend/app/controllers/api/work_items_controller.rb:51`.
- **V2.5.1.0.0.** Six handwritten adapter statements in the reminder batch are a joined replica read, a replica contact ownership read, and four timeout statements. Its report source aggregation also uses `select_all`. Reminder selection and exact revision matching use Active Record with handwritten predicates. The calendar uses Active Record with a PostgreSQL array-overlap fragment for reply reviews. See `backend/app/services/pms_refresh.rb:41–55`, `backend/app/services/contact_address_ownership.rb:33–39`, `backend/app/services/outcome_report.rb:37`, `backend/app/services/reminder_run.rb:34–56`, and `backend/app/controllers/appointments_controller.rb:10–12`.
- **V2.5.1.1.0.** The batch and calendar issue queries through Active Record. The database-side revision calculation lives in the handwritten `pms.versioned_appointments` view definition. The batch uses fragments for normalized contact lookup, stale-work reconciliation, and a `FOR SHARE` lock. The calendar groups on `start_at::date`. Leadership reporting also builds a handwritten join and group expressions inside an Active Record relation. See `backend/db/migrate/20261116000300_version_replica_appointments.rb:4–19`, `backend/app/models/contact_profile.rb:3–4,26–29`, `backend/app/models/reminder_batch.rb:44–53`, `backend/app/models/contact_directory.rb:5`, `backend/app/controllers/api/appointments_controller.rb:13`, and `backend/app/models/leadership_report.rb:29–42`.

The evidence includes the exact SQL and application stack for each observed statement. The Rails trace records adapter SQL even when the application supplied the text. The PostgreSQL server log independently records statements from clients and preserves protocol-level and setup activity. The static inventory is a syntax-tree inventory of Ruby calls with candidate labels. A relation declaration, an ordinary Ruby `map`, or a cached association read can occur without a database round trip. Ruby calls may share the same file and line, so the per-site observed count describes the line and cannot by itself identify which Ruby expression executed the query.

The inventory includes models, controllers, services, associations, callbacks, initializers, migrations, seeds, Rake and executable commands, tests, and React source paths. The test suites and supplemental probes reached all 43 declared API verb/path combinations across the three builds. Forty-two returned a success status at least once. The base build's `PATCH` assignment returned 404 for a missing record, and `PUT` successfully exercised the same assignment action. Full suites also invoke workflows directly. PostgreSQL statements that never ran in these scenarios have source evidence only. Lock placement and transaction statements are visible. Lock wait distributions, query plans on production-shaped data, unrelated local attempt history, and large numbers of clinics remain unmeasured by this matched workload.

The original used the normal scheduled worker method with one enabled clinic and the same dates and recipients. The original appointment request fetches the chosen week. The fixture has all appointments on the chosen day, so the expected response still has 2 or 24 appointments. The complete batch counts include seven commands from the original’s separate PostgreSQL connection, captured in the PostgreSQL server log. The original’s full Rails suite and shared code review remain separate checks.

### Audit execution corrections

The original’s first boot stopped on six missing locked gems. Installing those versions let the benchmark run. The first standalone audit setup reached scratch databases and stopped because Rails needed PostgreSQL's `psql` on PATH. The repeat supplied that directory and passed migration and the full Rails suites. The first common benchmark's JSON-encoded GET requests returned HTTP 404 in the integration driver. The driver was corrected to issue actual GET requests with query parameters. The first supplemental route pass used one invalid event identifier and one wrong fixture attribute. The final probes used the same contracts as the application and every probe returned its expected status. The first driver and probe logs and corrected logs are retained as distinct stages. Application code stayed frozen throughout the audit.
