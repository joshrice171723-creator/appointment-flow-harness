# V2.7.4.1.0 harness candidate

## Decision

Keep **V2.7.3.1.0 as the working harness baseline**. Its frozen application still has a recipient-safety gap, so the comparison does not establish a final candidate. V2.7.4.1.0 produced better exercised behavior and substantially less database work. Its application queries depend on handwritten SQL in database views and functions, which fails the agreed Active Record standard. Preserve the measured V2.7.4.1.0 result and the separate scoped refactor as evidence.

Both builds used the same assignment, shared prompt, model, effort, and host instruction hash. All four benchmark receipts match on case definitions, fixtures, trace instrumentation, and the outcome summarizer. The benchmark driver and adapter hashes differ across builds. The adapters use each build's normal entry points. Each checkpoint was archived to a private PostgreSQL database. The revised V2.7.4.1.0 adapter uses the app's fixture writer to simulate PMS changes outside the measured workflow. The first attempt stopped during setup when the read-only database guard rejected fixture writes. ### Evaluation against the four standards

| Area | Evidence and decision |
|---|---|
| Base | Both builds use normal Rails entry points with named workflow owners. V2.7.3.1.0 exposes the clinic lock and source failure path through `ClinicTransaction`. V2.7.4.1.0 places the hold, dispatch, and reply decisions in `ReminderRun`, `ContactPolicy`, and `PatientReply`. Its age boundary test demonstrates why the clinic-local outreach date matters. V2.7.3.1.0's four safety failures remain open. |
| Performance | V2.7.4.1.0 limits upcoming work and batches writes. The Rails callers use relation methods such as `where` and `group`. The relations obtain their contact keys, calendar decisions, and follow-up states from custom SQL in `pms.directory`, `workspace_visits`, and `workspace_follow_ups`. A reader has to follow the migrations to understand those query decisions. This is an application-query dependency, so the faster measurements do not qualify it for adoption. |
| AI loop | V2.7.4.1.0's review found material gaps and verified concrete repairs on the exact application tree carried into the freeze. Its performance rubric passed the SQL-backed projections. V2.7.3.1.0's review exercised repairs for malformed phone numbers, stale contact edits, and clearing contact values. Its internal gate passed while the four independent historical-contact failures remained. |
| Refactor | Each recorded isolated send-window exercise changed one production rule and checked neighboring behavior. The V2.7.3.1.0 exercise moved the closing hour and the V2.7.4.1.0 exercise moved the opening hour. The separately scoped V2.7.4.1.0 recipient trial preserved staff calendar results while applying plain Active Record to the existing workflow. The source lookup transferred more rows as clinic history grew. |

The source locations are the recipient policy, contact projection, workspace projections, email-key repair, and prior send-window exercise.

The archived code and matched results settle the choice of baseline. A further experiment would need to preserve the recipient behavior and performance gains using ordinary Active Record, with the actual query logic checked across model code and schema definitions. The existing scoped trial shows one valid direction alongside its measured read-growth cost.

The rebuild evaluation distinguishes Active Record calls from any computed representation required by their database. PostgreSQL evaluates an ordinary view when queried. An expression index stores the computed search key and adds maintenance work on source inserts and applicable updates. For a build that relies on this design, record who can install the schema objects, what the runtime role can access, and whether the executed plan uses the index on the exercised workload.
