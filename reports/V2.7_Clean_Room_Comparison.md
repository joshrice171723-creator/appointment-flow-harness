# V2.7.1.1.0 clean-room comparison

## First build checkpoint

V2.7 checkpoint `5fefe7d` passed all 16 shared benchmark checks. The endpoint results here compare that checkpoint with the frozen V2.6.1.1.0 build `b30516d`. V2.7's separate review found additional issues and recorded REVISE on this checkpoint.

| Measured operation | V2.6 statements | First V2.7 statements | V2.6 rows returned to Rails | First V2.7 rows returned to Rails |
|---|---:|---:|---:|---:|
| 24 eligible reminder sends | 18 | 43 | 99 | 99 |
| Retry the same 24 sends | 14 | 11 | 98 | 98 |
| Small staff appointments list | 8 | 8 | 9 | 9 |
| Confirming reply with 600 later appointments present | 18 | 17 | 9 | 609 |

- Both builds confirmed the exact intended source appointment, ID 1, in a focused rerun. The V2.7 trace shows one recipient-ownership query fetching ID, phone, and email for 602 patients. The test records Rails data transfer and statement counts. It leaves end-to-end production latency unresolved.
- Both versions wrote 49 rows for the 24 sends. V2.6 used 3 write statements and V2.7 used 26.
- V2.7 grouped calendar totals with plain Active Record using a stored clinic-local date and capped its day page at 25. That made the calendar query easier to follow.
- Independent review reproduced stale submissions, a reminder based on outdated source data, and unbounded reply loading inside an otherwise bounded inbox. The shared benchmark and the independent review cover different scenarios.

## Repaired build

V2.7 froze at `f48f82e` after two review rounds and about 90 minutes. The run used standalone GPT‑6.1 Sol High and the shared prompt, with optional skills, hooks, memory, and plugins disabled. The final technical grade was PASS under V2.7.1.1.0. All seven configured checks passed, including 30 Rails tests with 301 assertions and two React tests. Both Edge scenarios passed. The freeze commit changed documentation only from the application revision that cleared the gate.

The external benchmark ran on the freeze commit and passed all 16 workload checks. Exact source appointment ID 1 was confirmed on all five reply fixtures.

| Measured operation | Original statements / Rails rows | V2.6 statements / Rails rows | Final V2.7 statements / Rails rows |
|---|---:|---:|---:|
| 24 eligible reminder sends | 119 / 107 | 18 / 99 | 45 / 123 |
| Retry the same 24 sends | 38 / 151 | 14 / 98 | 11 / 98 |
| Small staff appointments list | 12 / 14 | 8 / 9 | 8 / 9 |
| Confirming reply with 600 later appointments present | 35 / 1,227 | 18 / 9 | 17 / 608 |
| Confirming reply with 2,000 additional patient records | 35 / 27 | 18 / 9 | 17 / 2,008 |

Repairs tightened stale-action and recipient checks, added a fresh source check before sending, and capped inbox reply loading. The recipient-ownership scan remains in the repaired build. The reviewer documented the need to compare differently formatted contact details and the absence of a normalized PMS address index or a contact change watermark. V2.6 moved fewer rows for the same confirmation in these fixtures. Supporting all cross-clinic and stale-revision cases with the same efficiency would require testing those contracts across the two implementations.
