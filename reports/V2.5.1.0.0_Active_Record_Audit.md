# V2.5.1.0.0 Active Record review

**Reviewed build.** Standalone Codex V2.5.1.0.0, commit `a04a25a6778829bfce3c3b010895b131527001b1`, using Active Record 8.1.4.1. The audit connects every SQL event from the saved runs to its source and the closest Rails example or API. It also reviews query paths that were visible in source and absent from those runs. Proposed changes are source findings. The application and its tests were left as recorded.

**Coverage.** 3,249 SQL events, including 24 Rails cache hits. There were 2,499 uncached application statements after removing Rails schema and connection setup from that subtotal. Those application events cover 94 source lines. The ZIP contains 109 source review entries and 285 formatted blocks from the guide indexed by chapter and example number. The block count includes Ruby examples, generated SQL, and console output. References point to the official examples. [Rails 8.1 Active Record Query Interface](https://guides.rubyonrails.org/v8.1/active_record_querying.html)

## What I would change first

| Priority | Where | What the code does | Change and evidence |
|---|---|---|---|
| 1 | `PmsRefresh#update_contacts`, lines 73–82 | Loads existing contacts to calculate changes. After its optional upsert, it reads the selected contacts again to get their IDs. | Keep the IDs already loaded. Return `patient_id` and `id` from `upsert_all` for changed or new records, then merge those IDs. The second lookup appeared **86 times** in the saved traces, including once on the 24-visit retry that did zero writes. Expect one fewer read on that path. Verify the ID map when all rows are unchanged and when new and existing contacts arrive together. [Bulk upsert and returning](https://api.rubyonrails.org/classes/ActiveRecord/Relation.html#method-i-upsert_all) |
| 2 | `InboundReply`, lines 40 and 110 | Tries to find a clinic contact even when the optional contact ID is nil. | Guard the lookup. The logs contain **9** contact queries with `id IS NULL` at these two lines. The primary key cannot be null. Keep the fallback for exactly one matching recipient, and keep the clinic scope when an ID is supplied. [Single record lookup](https://guides.rubyonrails.org/v8.1/active_record_querying.html#find-by) |
| 3 | `DemoPatientsController#index`, line 4 | Reads all columns from every contact in the clinic and serializes only `id` and `name`. | Use `select(:id, :name)` before serializing, or `pluck(:id, :name)` if the endpoint can build the lightweight response clearly. Keep the parent clinic lookup and current response shape. This reduces columns read. The app still needs a UI decision before paginating the picker. [Selecting fields](https://guides.rubyonrails.org/v8.1/active_record_querying.html#selecting-fields) · [Pluck](https://guides.rubyonrails.org/v8.1/active_record_querying.html#pluck) |
| 4 | `StaffFollowUp.call`, line 38 | Loads `item.contact` while creating an activity record. | The trace shows a separate contact read alongside the activity insert. If the activity only needs the foreign key, pass `contact_id: item.contact_id`. Verify that a nil association still works and the activity records the same contact ID. [Eager loading and association reads](https://guides.rubyonrails.org/v8.1/active_record_querying.html#eager-loading-associations) · [Persistence API](https://api.rubyonrails.org/classes/ActiveRecord/Persistence.html) |
| 5 | `ReminderRun#run` and `#load_batch_context`, lines 39–56 | Already batches the writes. Some inserts return IDs that the caller discards. The follow-up lookup loads complete work-item rows. | Check `returning: false` for the bulk writes whose result is unused. For the follow-up lookup, consider selecting only `id`, `work_key`, `detail`, and `resolved_at`. This is a payload improvement. The batch already has a good statement count. [Insert API](https://api.rubyonrails.org/classes/ActiveRecord/Relation.html#method-i-insert_all-21) · [Selecting fields](https://guides.rubyonrails.org/v8.1/active_record_querying.html#selecting-fields) |

Example for the contact-ID change. It reuses the existing map and keeps the current bulk write and unique key:

```ruby
ids = existing.transform_values(&:id)

if changes.any?
  saved_contacts = Contact.upsert_all(
    changes,
    unique_by: %i[clinic_id patient_id],
    returning: %w[patient_id id]
  )
  saved_contacts.each { |row| ids[row.fetch("patient_id")] = row.fetch("id") }
end

ids
```

The expected result is one less lookup after contact reconciliation. Confirm it on the same clock retry, on a mixed new-and-existing import, and on an empty import. The current dirty-tracking and rollback behavior still applies. [Upsert API](https://api.rubyonrails.org/classes/ActiveRecord/Relation.html#method-i-upsert_all)

| `OutcomeReport.source_outcomes`, lines 37–42 | Filter, group, and count in SQL | This is the cleanest conversion. A read-only source appointment relation can use a clinic ID set, a half-open date range, and a grouped count. Keep a short PostgreSQL expression for the month and compare the full report output across month boundaries. | `ContactAddressOwnership#replica_contacts`, lines 29–36 | Bind values, combine predicates with `or`, and return scalar fields with `pluck` | A read-only source patient relation can make the query easier to follow. Preserve the exact phone and email normalization expressions because the existing migration indexes those expressions. Ownership checks span the source population and must still catch addresses shared by different people. Preserve timeout and failure handling. [Placeholder conditions](https://guides.rubyonrails.org/v8.1/active_record_querying.html#placeholder-conditions) · [OR conditions](https://guides.rubyonrails.org/v8.1/active_record_querying.html#or-conditions) · [Pluck](https://guides.rubyonrails.org/v8.1/active_record_querying.html#pluck) |
| `PmsRefresh#read_source`, lines 38–55 | A left join preserves the clinic when its appointment collection is empty | Keep the current query while measuring it. The clinic row distinguishes a missing clinic from a valid empty clinic. The query also retains tracked appointments that moved outside the date window. The ordinary Rails association examples do not express that custom join condition by themselves. A rewrite should retain those cases and the meaning of a missing patient. [Left joins](https://guides.rubyonrails.org/v8.1/active_record_querying.html#left-outer-joins) · [Join fragments](https://guides.rubyonrails.org/v8.1/active_record_querying.html#using-a-string-sql-fragment) |
| `AppointmentsController#index`, lines 11–12 | Use a bound condition for comparison values | Keep PostgreSQL’s array overlap operator. Pass the selected IDs as a bound value with the same bigint array type instead of constructing the SQL list. Verify empty days, linked review items, and overlapping candidate IDs. The current values originated in the database. [Placeholder conditions](https://guides.rubyonrails.org/v8.1/active_record_querying.html#placeholder-conditions) |
| Refresh and address checks, `SET LOCAL` statements | Adapter and transaction APIs | These calls set a PostgreSQL timeout. They are outside the Query Guide’s relation examples. A change should preserve the operation’s time limit, transaction rollback, and the caller’s timeout after the read. [Adapter statement API](https://api.rubyonrails.org/classes/ActiveRecord/ConnectionAdapters/DatabaseStatements.html#method-i-execute) · [Transactions](https://api.rubyonrails.org/classes/ActiveRecord/Transactions/ClassMethods.html) |

A possible report query shape once a read-only source model exists:

```ruby
month_key = Arel.sql("to_char(start_at, 'YYYY-MM')")

Pms::Appointment.readonly
  .where(clinic_id: clinic_ids, start_at: from...until_date)
  .group(:clinic_id, month_key, :status)
  .count
```

This can make the query easier to understand without changing the aggregate work PostgreSQL performs. Compare the full result across clinics, months, time zones, and empty periods before swapping it in. [Grouping records](https://guides.rubyonrails.org/v8.1/active_record_querying.html#grouping-records)

## Query patterns already doing the right work

- **Check whether a threaded reply points to a delivered message.** `InboundReply:9` uses a scoped `exists?`. The trace shows a one-row existence check. The separate replay lookup loads its record because the code compares the old request’s contents. [Existence of records](https://guides.rubyonrails.org/v8.1/active_record_querying.html#exists-questionmark)
- **Detect an ambiguous unthreaded reply.** `InboundReply:97` asks for up to two distinct visit/revision pairs using `distinct.limit(2).pluck(...)`. Two pairs are enough to decide the reply is ambiguous. The staff review branch can still fetch the actual candidates. [Selecting fields](https://guides.rubyonrails.org/v8.1/active_record_querying.html#selecting-fields) · [Limiting records](https://guides.rubyonrails.org/v8.1/active_record_querying.html#limiting-records)
- **Preload the contact for a group of visits.** `ReminderRun:36` and `AppointmentsController:6` load visits and contacts in groups. That is the guide’s eager-loading example in practice. Several deliberate queries can be cheaper than repeating one per visit or joining everything into duplicated rows. [The N+1 problem](https://guides.rubyonrails.org/v8.1/active_record_querying.html#n-1-queries-problem) · [Includes](https://guides.rubyonrails.org/v8.1/active_record_querying.html#includes)
- **Count inside the database.** The appointment list’s weekly totals and the work board’s status buckets already use grouped counts. The board’s status totals apply to all clinic work. Its separate page count applies to the filtered list. Both outputs matter. [Grouped totals](https://guides.rubyonrails.org/v8.1/active_record_querying.html#total-of-grouped-items)
- **Keep exact revision keys and the transaction contract.** Reminder history joins on the visit and matches its current revision before plucking the few fields needed. Clinic locks and savepoints protect concurrent sends, invalid source data, and recoverable ownership failures. Prove those behaviors before changing transaction boundaries to save round trips. [Joining tables](https://guides.rubyonrails.org/v8.1/active_record_querying.html#joining-tables) · [Pessimistic locking](https://guides.rubyonrails.org/v8.1/active_record_querying.html#pessimistic-locking) · [Nested transactions](https://api.rubyonrails.org/classes/ActiveRecord/Transactions/ClassMethods.html)

## What the earlier benchmark measures

V2.5.1.0.0 used 26 statements at both 2 and 24 eligible reminders. On the 24-visit retry it used 22 statements and returned 241 rows while making zero writes. The raw refresh covers 14 days back through 30 days ahead plus tracked future appointments. A non-STOP reply also calls this refresh under the clinic lock. This is the next performance case worth testing. Keep the useful result fixed, add new source patients and appointments inside the refresh window that are outside the reminder window, and measure the replica query and whole operation. [Rails explain examples](https://guides.rubyonrails.org/v8.1/active_record_querying.html#running-explain)

Use query plans and result payloads for that test. The existing trace has statement count, result rows, affected rows, and duration. Rows scanned, transferred bytes, and lock waits need separate measurements. These are source and trace findings. A before-and-after run is still needed to measure the proposed changes.
