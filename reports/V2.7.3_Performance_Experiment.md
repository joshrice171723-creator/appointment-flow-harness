# V2.7.3.1.0 performance candidate

The hypothesis is that deciding how a consequential rule can be queried before implementing its read path will reduce repeated Ruby filtering and make the rule easier to change. The candidate adds that decision and its verification to the existing slice plan and rubric.

| Evidence | Candidate mechanism | External comparison |
|---|---|---|
| V2.7's recipient directory returned contact values for every source patient during a small reply operation. David's review also identified whole-collection reads for small decisions. | Identify the smallest answer and the representation its predicate needs. Consider an application-owned canonical value or relationship where the source representation prevents a scoped query. Require its freshness and update owner to be explicit. | Same reply and refresh fixtures with unrelated patient growth, changed values, and stale state. |
| The isolated controller refactor reduced loading by recreating complicated time-zone filtering in the query layer. | Evaluate the stored representation while the full rebuild can choose its schema. Account for duplicated domain calculations and where they must be updated. | Source review of rule ownership and a disposable rule change, alongside query cost. |
| A flat response or model count can hide a scan or a costly maintenance path. | Measure the complete operation and maintaining writes. Inspect plans for material scans. | Same workloads on frozen baseline and candidate, including unchanged retries and relevant growth. |

Rails documents scoped existence queries, projections, preloading, and query plans. Its migration DSL supports indexes and relationships. Its normalization API does not automatically rewrite historical stored values, so the candidate requires existing-data and write-path verification. These sources support the mechanisms. Whether the harness improves the build remains an experiment.
