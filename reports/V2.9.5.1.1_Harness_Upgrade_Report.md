# V2.9.5.1.1 harness upgrade

## ACTION

Add a mandatory task standard to the existing harness. Use ACTION, CONSTRAINTS, VERIFICATION, and REPORTING for every coding task. Apply the same standard to new projects, refactors, reviews, and repairs.

The standard includes writing rules, code quality requirements, six task examples, and a completion gate. Use the gate before reporting that a task is complete.

## CONSTRAINTS

Keep V2.8.5.1.1 and all earlier results. Add a separate version and clean-room run. Do not change the original application or its repository.

The new package keeps the same assignment, screenshots, and product requirements. It keeps the Active Record check, workload probe, command runner, and CI template. The new review criterion adds to the existing rubric.

The harness records a missing baseline when a new project has no runnable behavior. It requires checks when the behavior becomes available. This preserves the clean-room boundary and the requirement for actual evidence.

### Clean-room build result

The build froze the first implementation at `a0e5667` and the final result at `e26f412`. The builder's nine-criterion rubric recorded PASS on the final code. The complete local gate passed eight checks. It ran 32 Rails tests with 242 assertions and the Chrome workflow, reported zero RuboCop offenses and zero Brakeman warnings, and passed the Active Record source check. An independent reviewer ran six focused Rack tests with 42 assertions after the repairs. The runtime evidence covers the recorded clean-room application and its test data.

The first review found four problems. A concurrent PMS change could pair a new appointment time with an old confirmation. Ambiguous replies could be absent from the staff review filter. Successful corrected delivery left a hold open. An all-held reminder batch queried contact ownership before it checked for eligible sends. The first repair also caused a Rails callback error on several staff actions. The later changes fixed those paths. The app retained a known recipient's STOP even when outbound permission was already off.

That preserves recipient safety and leaves a database cost to measure in later versions.
