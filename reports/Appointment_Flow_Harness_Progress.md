# Appointment Flow harness progress

The experiment compares how coding instructions affect the quality of a Rails and React rebuild. Joshua set the priorities in this session: human readability, ease of changing a rule, and database work as data grows. The original `appointment-flow` was built over roughly a week and stays the historical baseline. The controlled rebuild comparison starts with the later standalone runs.

## How the experiment changed

- **Build guidance and review play different roles.** Early changes often told the reviewer how to describe the code after it existed. V2.6 asked the builder to measure realistic growth during implementation, preserve a checkpoint, then let independent review challenge the implementation. The separate benchmark still found the per-message writes after a rubric PASS. That prompted the measured follow-up and the stricter V2.7 grade.
- **Equivalent outcomes matter alongside query counts.** The shared benchmark ran five frozen builds against 16 checks each, including the original baseline. It measured statements, Rails rows, instantiated objects, written rows, and work on retry. The supplementary original run opened 16 staff tickets and sent 16 fake emails. Its retry created neither, even though it still read the source and checked existing work.
- **Good boundaries make edits easier to locate.** The V2.6 appointment controller kept daily totals, the review subset, and visible rows in one action. Joshua preferred keeping that screen-specific work in the controller with named private methods. Shared operations such as the reminder run belong in a service when their callers or business transaction justify it. The appended controller proposal is for review. It has no runtime effect.
- **Prefer plain Rails APIs.** We checked that grouping the leadership outcomes with Arel preserved results. Joshua preferred plain Active Record with a fixed query per month over adding a less familiar API to remove a string. V2.7 makes plain Active Record an application query rule.
- **Separate the evidence by environment.** The standalone V2.5 rebuilds and V2.6 used the same assignment and launch prompt. Three RubyMine AIR projects were prepared. The dashboard tracks them separately from the five measured builds. Refactor and feature-delivery use cases were discussed as modes for the same harness and remain outside this rebuild evidence.
- **Regrade under the standard being evaluated.** V2.6's frozen app earned REVISE under V2.7. The regrade found query and controller-structure violations and reproduced an old open task bypassing missing-source detection. The new calendar filter checks and the fresh 29-test Rails suite passed. [V2.7 regrade of the frozen V2.6 app](V2.7_Regrade_of_V2.6.md)
