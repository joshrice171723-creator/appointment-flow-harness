## What the comparison supports

The isolated refactor is the strongest measured performance candidate. It bounds opt-out reads to relevant destinations, selects history and replies in the database, and filters past visits before loading their complete context. The first refactor is the closer match to the original's observed read timing.

The remaining concurrent response difference is a compatibility finding. The API has no documented point-in-time snapshot guarantee. The check injects a write after a particular source read, and changing read order changes which committed state is visible. This does not establish a wrong-recipient or write-safety defect. Future checks should assert business invariants as well as identify timing differences, without turning incidental original query order into a new product requirement.

My source review prefers the isolated version's short public dispatch between calendar and upcoming views. Its upcoming filter requires reasoning about UTC offsets, gap and fold windows, earlier concurrent inserts, and changed clinic settings. The model still owns the actual wall-time conversion. Maintaining both calculations is a concrete reading and change burden. The first version reuses conversion directly but transfers more data.

Both builders graded REVISE because the shared source-freshness owner still reads PostgreSQL's clock with SQL. The isolated trial also reproduced the same full-suite query-budget failure on the original and its refactor at seed 31326. Each ran 118 tests with 1,796 assertions and one failure. The earlier first-refactor run passed 118 tests and 1,797 assertions under its own recorded conditions. This comparison does not turn that earlier pass into a matched-seed pass.

## Decision and next experiment

Keep the isolated launch preparation. Preserve both refactors as evidence. Treat the isolated implementation as the better measured performance direction, with a remaining read-timing difference and substantial time-zone complexity.

The next full rebuild should test whether designing queryable data and its update owner early produces efficient, simpler queries. The controller-only restriction prevented that choice here. First build the unchanged V2.7.2.1.0 harness as a full baseline, then compare one targeted performance revision under the same launch conditions. Keep both old implementations and these results outside their builder contexts.

The global host AGENTS.md remained active in both trials. It contains Joshua's general engineering and copy instructions and was last modified before the trials. Optional skills, hooks, plugins, and prior-project memory were disabled. Historical project guidance and the prompt search boundary were the changed conditions.
