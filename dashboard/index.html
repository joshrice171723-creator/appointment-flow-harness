How the original job turns appointments into staff work

Appointment Flow keeps front-desk staff informed when patients cannot be reached or still need to confirm. Its Sidekiq worker runs at startup and every five minutes. It keeps appointment facts current, updates the work queue, and sends reminders when a clinic is due.

  1. Set up the demo replica. setup_replica.rb creates a separate PostgreSQL database, runs the PMS migrations, and loads fictional clinic, patient, and appointment records. Setup uses a writable connection and grants the runtime reader SELECT access. This is the demo’s stand-in for the scheduling system’s replica.
  2. Refresh the app’s local copy. Each tick reads all replica clinics and patients. Appointment reads normally start at the beginning of the previous month and also include tracked appointment IDs that may have moved outside the range. PostgreSQL returns one JSON array per table. Rails parses and bulk upserts those facts into the app database, skips rewriting unchanged source rows, and records the last successful sync. Sends are suppressed if refresh fails.
  3. Work out what needs attention. The app reconciles its local visits against the refreshed appointment facts. If a visit changes, the job can retire the old visit and close follow-ups that no longer apply. It checks each relevant current visit for a usable, permitted contact and whether the patient still needs to respond.
  4. Save staff work and record reminders. The app writes its results to its own database. A database lock and a once-per-day marker protect each clinic’s sends. Subsequent ticks still refresh and maintain the queue even if today’s sends are already complete.

The front-desk page reads cases already in the app database. If the assessment demo history is enabled, setup also replays synthetic reminders, replies, and staff actions, so some tickets or their history can already exist before the worker starts.

Original source used in this audit

What opens a ticket

Contact issue. A visit is due for outreach but the app cannot safely message the patient. Examples include a missing address, a contact conflict, or a restricted channel.

No-response issue. The patient can be contacted, the appointment is within 48 hours, and the job sees neither a confirmation nor a handled response. This rule can open an issue on the first tick when a visit is close enough.

Delivery issue. The sender reports a failed attempt. Patient replies that need clarification can open review work through the reply workflow.

The app stores the reason on an issue tied to a visit and groups issues in one front-desk case per patient and clinic. It reuses an existing issue for the same visit and reason category, reopening or updating it when necessary, and records an activity event for a new issue.

What a reminder writes

The job chooses SMS or email, formats the appointment time and clinic, and asks for confirmation or help when appropriate. The demo uses a fake sender and stores each attempt. A message can cover more than one purpose, such as an initial request and a day-before reminder.

Each attempt records a message with its delivery status, one or more rows linking it to its reminder purposes, and an activity event. The patient’s reply is a separate request.

In the shared 24-due first run, the original persisted 24 messages, 24 purpose rows, and 24 activity events. Every synthetic patient had usable email and was seven days out, so no staff tickets were created. That run made 119 statements and affected 170 rows across the job.

Measured first run with tickets and reminders

A separate test ran the original job at noon for one clinic with 24 fictional appointments. Eight were seven days out with valid email, eight were the next day with valid email and no response on record, and eight were seven days out with no usable contact.

First tick. The original opened 16 tickets for 16 patients. Eight were contact issues and eight were no-response issues. The ticket work wrote 16 case rows, 16 issue rows, and 16 issue-opening activity events.

It also recorded 16 simulated emails, 24 reminder-purpose rows, and 16 delivery activity events. Each email body was 108 bytes, or 1,728 bytes of body text in total. That excludes message metadata and delivery-provider overhead.

The whole tick made 239 database statements, including 104 write statements. It affected 202 rows, returned 171 rows to Rails, and instantiated 86 Rails models.

Same-clock retry. The job created zero new tickets and zero new messages. It still read the source and checked the existing queue. The 88 database statements included six write statements. Only the last-sync row was affected.

Rails instantiated 156 models on retry, including 64 visit objects and 48 follow-up issue objects. Repeated loads count each time, so the number can rise as the app has more existing work to check.

Each tick fetched 8,893 bytes of replica JSON across three reads. Seven replica statements, including connection-level transaction commands, are already included in each total.

How much data the original imports

The original uses Active Record for the staff appointment list and handwritten SQL for PMS import and advisory locks. The first 24-reminder run fetched 9,045 bytes of replica JSON. With two reminders due and 600 later appointments, it fetched 230,214 bytes and still sent just two reminders.

Those byte counts cover the source JSON arrays. The reminder bodies and database storage have their own costs. The shared fixture used one clinic per case.

V2.7.4.1.0 full rebuild decision

Keep V2.7.3.1.0 as the working harness baseline. The V2.7.4.1.0 rebuild relies on handwritten SQL in views and functions for recipient matching and staff views. That fails the plain Active Record standard. The baseline's recipient safety and database growth gaps remain open.

Behavior. V2.7.3.1.0 passed 40 of 44 matched checks at both checkpoints. It confirmed three ambiguous replies and sent one reminder to a shared number. V2.7.4.1.0 passed all 44 at both checkpoints. It routed the ambiguous replies to staff review and held the unsafe reminder.

Database work. With 600 later appointments added, the reviewed V2.7.3.1.0 build sent two reminders in 1,228 statements. The reviewed V2.7.4.1.0 build sent the same two in 16 statements. A successful confirming reply went from 3,019 rows returned to Rails to six. The reviewed appointment list loaded one more Rails record in V2.7.4.1.0 and used one fewer statement.

Scoped refactors. The earlier refresh trial cut the first reminder run from 1,228 to 26 statements while still affecting 1,207 rows. The separate V2.7.4.1.0 recipient refactor used plain Active Record and passed all 44 checks. Its historical reply transferred 614 rows with 600 additional owners, compared with 14 on the small fixture. That growth remains an open cost.
